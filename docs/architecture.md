# SkySathi Production Architecture (Stage 5)

## 1. Project structure — why every folder exists
`mobile/` holds the React Native client: `src/screens` (one file per surface, ported pixel-for-pixel from the Stage 4 prototype, which remains the design spec), `src/components` (StatusBand, NarrationCard, and other pieces shared across screens), `src/hooks` (useSensors, useFlightPhase, useAnxiety — all stateful device logic lives in hooks so screens stay dumb), `src/services` (api client with refresh + offline queue, storage, tts), `src/ai` (the on-device intelligence: phase detector, anxiety engine, offline KB — pure TypeScript, no React imports, so it is unit-testable and portable), `src/state` (zustand stores: session, profile, journal), `src/i18n` (en/hi from day one), `src/theme` (the design tokens — no red, 56 px targets, Atkinson Hyperlegible), `__tests__` (golden-vector and component tests). `api/` holds FastAPI: `app/routers` (thin HTTP layer), `app/services` (all logic; `services/ai` is the engine cluster), `app/models.py` (the schema is one reviewable file on purpose), `tests`. `shared/` holds cross-language contracts — currently the phase-detector golden vectors, later prompt snapshots and KB schemas. `docs/`, `.github/workflows`, and root compose/config round it out. Assets and animations (Lottie for the breathing orb and confetti) live under `mobile/assets` once designed; authentication, database, storage, utilities, localization, testing, configuration and deployment are not separate top-level folders but concerns mapped into the structure above — a folder per concern in a small team is bureaucracy, a folder per runtime is clarity.

## 2. Mobile application
Navigation: bottom tabs (Home, Flight, Calm, Journal) under a native stack that hosts modal Chat, Settings, SensorLab, Wallet, Weather, Family, Academy. Calm is one tap from anywhere during an active flight — that is the product promise encoded in navigation. State: zustand (tiny, no boilerplate, selector-based re-renders) with MMKV persistence; server state via plain fetch + the offline write queue rather than a heavy query library, because the app's core loop must work in airplane mode. Offline: the KB, aircraft data, airport pack, and wallet ship in the bundle; all writes queue in MMKV and flush on reconnect; conflict policy is last-write-wins per field (journal notes) and append-only elsewhere. Background: Android foreground service whose persistent notification IS the status line ("Cruising · everything is normal"); iOS uses location background mode with barometer sampling, and the Live Activity on the lock screen mirrors the status band. Sensors: consent-gated per sensor, 10 Hz accelerometer, 1 Hz barometer (primary), duty-cycled GPS; all feature extraction in a JSI worklet thread. Permissions: each request appears in context with plain-language purpose (the app.json strings are user-facing copy, not legal filler). Deep linking: `skysathi://flight/<no>` and `https://share.skysathi.app/f/<token>` for family view. Push: APNs/FCM via expo-notifications; boarding and gate-change notifications are local-first (scheduled on-device from the countdown) so they fire with zero connectivity. Platform specifics: iOS Live Activities and precise barometer; Android widget with the status line; both get haptics on phase transitions (gentle, opt-out).

## 3. Backend API architecture
FastAPI, async SQLAlchemy, thin routers over services. Resource groups: `/auth` (guest-first: a guest IS a user row; social/email linking upgrades it — zero-friction onboarding without data loss), `/users` (me, export, GDPR delete), `/flights` (CRUD, history, sensor-window ingestion, turbulence network read), `/conversations` and `/genai` (the only LLM call sites, via the GenAI pipeline), `/preferences`, `/premium` (server-side receipt verification — the client never decides entitlement), `/notifications`, `/feedback`, `/analytics` (consent-gated, pseudonymous, with a banned-props policy enforced server-side), `/version` (min-supported gate + KB/detector versions so the client knows when to refresh bundles). Middleware: request-id tracing, per-IP token bucket now, Redis-backed rate limit at scale. Versioning: URL-stable, additive changes only; breaking changes get `/v2` (expected never).

## 4. Database
Postgres 16 + pgvector. Core spine: users → flights → flight_sessions → sensor_events (aggregated windows only; raw never leaves devices; 90-day retention post-aggregation). users 1-1 preferences and premium; 1-many conversations→messages, achievements, journal_entries, notifications, feedback, audit_logs. turbulence_reports is deliberately user-less (route_cell + time_bucket + energy) — k-anonymity by schema, not by promise. kb_chunks carries 1024-dim bge-m3 embeddings for RAG. refresh_tokens enables rotation and theft detection (reuse of a revoked jti). analytics_events is pseudonymous product telemetry. Soft-delete on users with a nightly hard-purge job satisfies deletion law without losing referential integrity mid-request.

## 5. Authentication
Guest mode is the default and is a first-class account: `/auth/guest` issues a JWT pair instantly, so an anxious first-time user reaches the calm tools in zero taps. Google and Apple sign-in verify platform ID tokens server-side and link to the same row via oauth_sub. Email uses bcrypt + register/login; password reset via emailed one-time token (15-min TTL). Access tokens live 15 minutes; refresh tokens 30 days with rotation — every refresh revokes the old jti, and reuse of a revoked jti flags theft and revokes the family. Account deletion is one endpoint, soft-then-purge, audit-logged. Privacy controls (export, erase, memory toggle) exist identically on-device and server-side.

## 6. Cloud architecture
Chosen: **GCP Cloud Run + Cloud SQL Postgres (pgvector) + Memorystore Redis + Cloudflare in front**, with Firebase used ONLY for FCM. Reasoning: Cloud Run scales to zero (an India-first startup's traffic is spiky around flight banks; paying for idle EC2 is waste), Cloud SQL keeps pgvector (Supabase would also work and is the recommended fallback if we want managed auth + storage in week one — but our auth is custom for guest-first, which Supabase auth handles awkwardly), and Cloudflare gives CDN, WAF and rate limiting at the edge for free-tier prices. AWS is the safe giant but its equivalent (App Runner/Fargate) is pricier at zero scale; Azure has no advantage for this stack. Secrets: GCP Secret Manager, injected as env vars at deploy; no secret ever in the repo, `.env.example` documents the shape. Storage: GCS for journal photos behind signed URLs. Monitoring below. Environments: dev/staging/prod as separate GCP projects, config only via env.

## 7. AI backend: a fixed GenAI pipeline
Every chat message passes once through six stages in a fixed order, implemented as plain functions in `api/app/ai/pipeline.py`: (1) NLP preprocessing (`nlp.py`: normalisation, tokenisation, EN/HI/Hinglish language-ID, entities); (2) ML classifiers (`classifier.py`: TF-IDF + Logistic Regression for anxiety band and intent, plus a panic safety lexicon); (3) hybrid RAG retrieval (`rag.py`: BM25 ⊕ MiniLM transformer embeddings with Reciprocal Rank Fusion over `kb/knowledge.yaml`); (4) prompt assembly (`prompts.py`: persona, audience, anxiety policy from `explanation.py`, few-shot, KB context with citation rule, live state, memory from `memory.py`); (5) LLM generation (`llm.py`, any OpenAI-compatible endpoint); (6) guardrails (`guardrails.py`). The LLM only writes text. It never selects tools, loops or acts. With no key, stage 5 is replaced by an extractive answer built only from retrieved facts. `evaluation.py` scores generated content against the product objectives, and `lab_router.py` exposes all of it at `/genai/*`. The Recommendation Engine (`recommendation.py`) ranks suggested questions separately.

## 8. Performance
Startup budget: interactive home under 1 s — Hermes, no network on the critical path (guest token fetch is deferred), fonts bundled, first screen renders from MMKV. Memory: ring buffers for sensor windows, zero per-sample allocation. Battery: barometer-first sensing, GPS duty-cycling per phase, feature extraction on the worklet thread, target <2%/hour in flight mode. Rendering: FlatList everywhere lists exist, memoized cards, no shadow-heavy views on the hot path. Caching: LLM prompt-prefix caching (static persona + few-shot prefix first), Redis for turbulence-cell reads, HTTP cache headers on /version and KB bundles. Offline sync: append-only queues, exponential backoff flush. Images: journal photos resized on-device before upload, served via signed CDN URLs. Bundle: academy content and wallet lazy-loaded behind navigation; target <25 MB Android AAB.

## 9. Security
Transport: TLS 1.2+ only, HSTS at Cloudflare. At rest: Cloud SQL encryption; on device MMKV encrypted with a keystore key, wallet documents additionally wrapped by a biometric-gated key. API: JWT auth on everything but /health and /auth, per-IP and per-user rate limits, Pydantic validation on every body (lengths capped, enums enforced), banned-props policy on analytics. Secrets in Secret Manager, LLM key server-side only. Authorization: every query filters by the token's user_id — no object-level trust of client ids. Privacy: raw audio and raw sensor streams never uploaded by architecture; anxiety scores never uploaded by policy enforced in the analytics router; turbulence contributions k-anonymized by schema. Security logging: audit_logs rows for login, refresh rotation, export, deletion; alerts on revoked-jti reuse. Dependency scanning via Dependabot; one annual external pen test before any airline partnership conversation.

## 10. Testing strategy
Layered: unit tests for the pure modules (detector, anxiety, retrieval scoring) — the golden-vector suite in `shared/` is the crown jewel and runs in BOTH languages in CI so the twins can never drift. Integration: httpx TestClient against a dockerized Postgres for auth flows, chat pipeline (LLM mocked), premium verification. UI: React Native Testing Library for components; Maestro flows for the five critical journeys (onboard, start flight, panic path to Calm, ask a question offline, complete + rate). Sensor simulation: recorded real-flight logs replayed through useSensors as fixtures — every recorded flight becomes a regression test. AI testing: prompt snapshot tests (system prompt for a fixed context must match the approved snapshot) plus a rubric-scored eval set of 50 anxious-flyer questions re-run on every prompt change. Accessibility: axe checks in component tests, manual VoiceOver/TalkBack passes per release, and the four a11y modes each have a smoke test. Performance: startup-time and battery budgets asserted on real devices in the release checklist. Beta: TestFlight + Play internal track, then a 50-user closed beta recruited from fear-of-flying communities. Crash reporting: Sentry RN + FastAPI SDKs from day one.

## 11. Monitoring
Sentry for crashes and API errors (release-tagged, request-id correlated). Product analytics: PostHog self-hosted (data residency + cost) — funnels for onboard→first flight→second flight, retention cohorts by fear type, feature usage on Calm/WWT/Chat. AI quality: per-reply latency, token cost, fallback rate (offline answers vs LLM), thumbs-up rate on answers, and weekly sampled human review of 50 conversations under a privacy-safe review policy (opt-in only). Latency: p50/p95 per endpoint in Cloud Run metrics with alerts at p95>1.5 s on /conversations/chat. The one metric that matters: post-flight calm rating trend per user — the product exists to move it.

## 12. CI/CD & deployment
GitHub Actions: on every PR — lint, both golden-vector suites, api pytest, mobile jest; merge to main deploys api to Cloud Run staging automatically. Tags `v*` trigger: EAS build (iOS+Android) → EAS submit to TestFlight/internal track → staged rollout (10%→50%→100% on Play; phased release on App Store) → api image to prod with `gcloud run deploy` (revisions give one-command rollback). Versioning: semver, /version endpoint gates minimum client. Store rollback: halt staged rollout + `eas submit` previous build; DB migrations are expand-migrate-contract so an old client never breaks against a new schema.

## 13. Business model
Free tier is the trust engine: full calm tools, demo flight, academy, one live flight per month — the panic button is never paywalled, ever (both ethics and the growth loop: the person you calm tells three people). Premium ₹149/flight via UPI (impulse-priced at the gate, the highest-intent moment in the funnel) or ₹1,299/year for unlimited flights, family mode, wallet sync, and priority AI. Family plan ₹1,999/year for four members with shared tracking. Enterprise: airline white-label ("IndiGo Calm, powered by SkySathi") sold per-PNR — airlines pay for reduced cabin-crew load and NPS lift; airport partnerships license Airport Mode content (DEL T3 pack sponsored by the operator); travel companies (MakeMyTrip/Cleartrip) get an affiliate API: attach SkySathi Premium at booking for anxious-flyer-flagged customers. Revenue sequencing: consumer UPI first (proves willingness to pay), annual second (proves retention), B2B third (needs the first two as evidence).

## 14. Final review — known weaknesses and their mitigations
Weakest points, honestly: (1) phase detection is untested on real flights — mitigation: the recorded-flight fixture program is the first Stage 6 task and every fixture becomes CI; (2) LLM dependency on the emotional core — mitigation: the offline KB path is a full-quality fallback, and prompt snapshots stop silent drift; (3) single-founder bus factor — mitigation: this document, golden vectors, and boring technology choices; (4) push notification delivery in airplane mode is impossible — mitigation: boarding reminders are local-scheduled, family notifications are honest about "sent when connectivity allows"; (5) the turbulence network is empty at launch — mitigation: seed with public PIREPs/EDR data until crowd density arrives. Scalability posture: Cloud Run scales the stateless API horizontally; Postgres vertical headroom covers the first million users; the only true fan-out (family notifications) goes through a queue from day one.
